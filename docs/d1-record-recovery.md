# D1 损坏资料隔离与选择性恢复

日期：2026-10-25。本轮完成损坏记录保全、可见异常提示、恢复预览和逐项恢复。恢复始终生成新资料库，原库不原地修复或覆盖。

## 发现损坏时的行为

- JSON 记录按 ID、JSON 结构和 32 MiB 上限校验；SQLite 记录按相同规则校验。2026-10-26 补充已知嵌套类型、历史生产格式的必要字段及比较表内部定位检查，迁移也通过统一解码并检查当前比较文献；见 [必要字段与迁移说明](d1-record-contract.md)。检查不等于全部业务语义或所有跨记录关系验证，已保存证据、材料和历史不强制匹配当前源版本。被识别的坏记录独立隔离，健康记录及已保存证据快照继续可读。
- 原始坏字节留在原路径，同时复制到 `quarantine/records/<sha256>.bin`，旁边保存不含正文的元数据。复制失败时只报告保全失败，不删除原件或猜测恢复内容。
- 中断写入留下的 `*.tmp` 不会自动覆盖主记录，作为待核对异常显示。错误、权限、符号链接和不安全目录也会进入资料库健康信息。
- 桌面页面显示异常数量和路径；笔记、比较表和成果仍能显示保存时的证据快照，并明确提示原文记录损坏或无法定位。损坏记录不能继续编辑或发送给模型。
- API 将记录损坏区分为 `RECORD_CORRUPT` 和 `RECORD_UNAVAILABLE`，客户端不会把这类错误当作可重试写入，也不会声称提交结果未确认。

## 预览与恢复

“选择性恢复损坏资料…”先让用户选择目录或 ZIP 备份，生成恢复清单。每个项目列出记录／原文件路径、备份版本、可用的中断写入版本和是否同时恢复匹配原文件。用户逐项选择，最后确认总范围；跳过的项目继续隔离。

执行前重新检查当前异常项目、备份清单和预览 revision。异常项目、候选版本或备份变化会要求重新预览；无关健康记录在预览后产生的新修改会进入恢复副本。恢复流程随后：

1. 复制并校验当前资料到 `library-backups/<uuid>`，作为原件保全副本。该副本可能包含损坏内容，不声明数据库逻辑完整性。
2. 把当前资料复制到新的暂存目录，只替换用户选中的记录和匹配原文件，保留其他记录在恢复前的较新修改。
3. 对选中文献，将旧的 pending/failed 原文件待办标记为 `SUPERSEDED_BY_RECOVERY`，只在恢复副本中停止重放；原库及保全副本的原日志保持不变。
4. 重新校验恢复后的记录，写入恢复报告并发布为新资料库。目标启动和位置保存成功后才切换桌面窗口。

恢复发布前进程被 SIGKILL 时，原库、保全副本和暂存目录都保留；可使用新目标与新保全目录重新执行，不自动续写上次的恢复暂存目录。目标目录已存在、目录锁被占用、候选哈希变化或目标启动失败都会停止，不覆盖已有内容。

## 离线工具

关闭应用后使用：

```sh
node tools/storage-maintenance.mjs preserve /path/to/library /path/to/preserved-copy
node tools/storage-maintenance.mjs recovery-preview /path/to/library /path/to/backup [directory|zip]
node tools/storage-maintenance.mjs recover /path/to/library /path/to/backup /path/to/new-library /path/to/preserved-copy /path/to/selection.json
```

选择清单是 `recovery-preview` 的 JSON 输出，需保留 `revision`、`format` 和明确的 `selections` 数组。工具不会从损坏库自动推断恢复版本。
